# Multik Sila — VPN-клиент на Flutter (Windows)

GUI-клиент поверх sing-box и Xray-core для VLESS/VMess/Trojan/Hysteria2, в стиле Karing.
Вся логика в одном файле: [lib/main.dart](lib/main.dart) — парсинг подписки, генерация
конфигов на лету, управление процессами ядер, UI.

**Git-репозиторий есть** (ветка `main`), но в нём пока ОДИН коммит — «фикс петли
маршрутизации в TUN + раздельное туннелирование». Всё, что сделано после, лежит
незакоммиченным: локализация, переводы лога, статистика, QR, NTP, раздельные
GeoSite/GeoIP, правила для программ, автообновление ядер, экраны сети и конфигов.
Стоит закоммитить до следующего раунда правок — иначе единственная страховка от
регрессии это ручное тестирование.

## Критические грабли (не наступать снова)

1. **`ProductName` в `windows/runner/Runner.rc` — НЕ ТРОГАТЬ.** `shared_preferences`/
   `path_provider` на Windows строит путь к данным как `%APPDATA%\<CompanyName>\<ProductName>\`,
   беря оба значения из VERSIONINFO-ресурсов .exe. Однажды меняли ProductName при
   ребрендинге — приложение тут же "потеряло" все сохранённые профили (они физически
   остались в старой папке, просто новый ProductName указывал на другую). Название
   приложения меняется только через: `MaterialApp.title`/`AppBar` в main.dart,
   нативный заголовок окна в `windows/runner/main.cpp` (`window.Create(L"...", ...)`),
   и `FileDescription` в Runner.rc. `ProductName`, `CompanyName`, `OriginalFilename`,
   `InternalName`, имя самого .exe и `BINARY_NAME` в CMakeLists.txt — всегда
   `proxy_app_test` / `com.example`, независимо от отображаемого названия.

2. **Убивать посторонние процессы по ИМЕНИ нельзя вообще нигде — исправлено.**
   Раньше `_killStrayXray()` делал `taskkill /IM xray.exe /F` перед стартом своего
   ядра. Под этим именем работает личный v2rayN пользователя, поэтому каждый запуск
   xhttp-сервера в обычном режиме рубил ему интернет. Обе функции заменены на
   `_killStrayOnOurPorts()`: `netstat -ano` → PID владельца НАШЕГО порта
   (`localPort`, `clashApiPort`, мосты 1338+) → `taskkill /PID`. Историческое
   обоснование, почему это важно: У пользователя параллельно
   работает СОБСТВЕННЫЙ v2rayN (тоже поднимает `xray.exe`/иногда `sing-box.exe`-стайл
   процессы), и это его основной канал в интернет — в том числе то, через что он
   переписывается с Claude в этом самом чате. Убийство по имени процесса валит
   заодно и его. Внутри приложения killStray* используется только непосредственно
   перед стартом СВОЕГО ядра. Везде, где нужно остановить конкретный процесс
   приложения — используется `Process.kill()` по хендлу, не по имени.

3. **Elevated-процессы нельзя убить обычным (неэлевированным) `taskkill`** — Windows
   Mandatory Integrity Control не позволяет процессу среднего уровня целостности
   убить процесс высокого уровня, даже под тем же пользователем. Если что-то из
   TUN-тестирования зависло с правами администратора — единственный способ убрать
   это из bash-сессии: `PowerShell.exe Start-Process taskkill -ArgumentList
   '/PID','<pid>','/F' -Verb RunAs -Wait` (снова спросит UAC).

4. **Нет инструмента для клика по нативному Win32-окну.** Проверка функциональности
   всегда идёт так: сгенерировать точно такой же JSON, какой построил бы Dart-код
   (вручную или через одноразовый чистый Dart-скрипт в scratchpad, копирующий
   актуальные функции парсинга), запустить `sing-box.exe`/`xray.exe` напрямую через
   Bash, дёрнуть через `curl`/Clash API. Только после того, как логика подтверждена
   в CLI — пересборка и передача пользователю "запусти и скажи что вышло".

5. **UAC-тесты TUN-режима — дорогая операция для пользователя** (каждый прогон —
   реальный клик мышью). Всегда: (а) сначала `sing-box.exe check -c config.json`
   (не требует прав, ловит синтаксические ошибки бесплатно), (б) весь сценарий
   (старт + проверка + гарантированная остановка) в ОДНОМ elevated PowerShell-
   скрипте с `try/finally`, чтобы не оставить недобитый процесс и не просить
   второй UAC на откат.

## Архитектура

### Два ядра
- **sing-box.exe** — основное. Понимает VLESS/VMess/Trojan/Hysteria2 и **нативный TUN**.
  НЕ понимает транспорт `xhttp` вообще (проверено по исходникам — в дереве sing-box
  нет ни единого упоминания xhttp/splithttp).
- **xray.exe** (официальный релиз XTLS/Xray-core, лежит в корне проекта) — только для
  серверов с транспортом `xhttp` (в подписке пользователя это ~5 из 15 серверов:
  <xhttp-сервер 3>/X, <xhttp-сервер 5>, <xhttp-сервер 2>/XR). Xray **не имеет** нормального нативного TUN.

`ParsedServer.engine` = `'singbox'` или `'xray'` — определяется в парсерах
(`parseVless`/`parseVmess`/`parseTrojan`) по `type=xhttp` в ссылке.

### Обычный режим (не-TUN) — локальный прокси на 127.0.0.1:1337
- singbox-серверы: все грузятся разом в один `selector`-outbound, переключение —
  мгновенный `PUT /proxies/proxy` через Clash API (порт 9090), без рестарта процесса.
- xray-серверы: единственный outbound, переключение — полный рестарт `xray.exe`
  (у Xray нет аналога Clash-селектора).

### TUN-режим — системный VPN
Включается тумблером в UI. Требует прав администратора — но НЕ элевируется отдельный
дочерний процесс (это ломает `kill()`/лог и просит UAC дважды на старт/стоп), а
**перезапускается само приложение** целиком (`_restartElevated()`), тогда дети
наследуют elevation бесплатно.

- sing-box держит `tun`-инбаунд (адаптер `SilaTUN`, IPv4+IPv6) и весь роутинг.
- Для xhttp-серверов — **постоянный мост на Xray для КАЖДОГО сервера отдельно**,
  на своём выделенном порту (1338, 1339, ...), поднимаются все разом перед стартом
  sing-box и живут весь TUN-сеанс (`_ensureAllXrayBridgesRunning`). Критично: sing-box
  запекает `server_port` outbound'а в конфиг при старте и НЕ может поменять его на
  лету через Clash API — поэтому один общий порт с убийством/рестартом при
  переключении устраивал гонки ("connection refused"/"forcibly closed"). Раздельные
  постоянные мосты = переключение между xhttp-серверами это чистый Clash API switch.
- Мост — **SOCKS5 с `udp: true`**, не HTTP-прокси. HTTP-транспорт физически не
  переносит UDP, а браузеры сегодня часто пробуют HTTP/3 (QUIC/UDP) — с HTTP-мостом
  это давало `router: UDP is not supported by outbound`.
- DNS в TUN-конфиге: фиксированный detour через sing-box-нативный сервер (НЕ через
  активный selector) — иначе при активном xhttp-мосте DNS пытается пойти через
  HTTP/SOCKS-transport, что для UDP-DNS ломается. Плюс отдельное правило: домены
  самих прокси-серверов резолвятся напрямую (`dns-direct`), иначе циклическая
  зависимость (нужен IP сервера, чтобы к нему подключиться и тем самым резолвить его же).
- **Петля маршрутизации на собственном xray.exe — главная причина обрывов под TUN.**
  `auto_route: true` заворачивает в туннель трафик ВСЕХ процессов машины, включая наш
  же `xray.exe`, который держит мост. Его собственный коннект до прокси-сервера
  попадал в TUN, sing-box по `route.final: "proxy"` отправлял его в активный outbound —
  а если активен как раз xhttp-сервер, то это socks-мост, то есть **обратно в тот же
  xray**. Замкнутый круг: трафик ходит по кольцу, наружу не выходит.
  Симптом в UI: `Отправлено` растёт, `Скачано: 0 Б`, число активных соединений пухнет;
  в браузере — `ERR_CONNECTION_RESET`. Своё ядро sing-box из туннеля исключает сам
  (`auto_detect_interface`), но про посторонний процесс не знает ничего.
  Лечение — `route.rules` в `_writeConfig`: `process_path` на наш `xray.exe` →
  `direct`, плюс страховка `ip_cidr` с заранее отрезолвленными IP прокси-серверов
  (`_resolveToCidrs`) на случай, если process-матчинг на Windows не сработает.
  **Исключать по `process_name: ["xray.exe"]` НЕЛЬЗЯ** — под этим же именем работает
  личный v2rayN пользователя, и такое правило молча увело бы его трафик мимо VPN.
  Резолвить хосты надо на этапе генерации конфига: когда TUN уже поднят, DNS-запрос
  сам поедет в туннель.
- ~~`dns-direct` без явного `"detour": "direct"` прямым НЕ является~~ — **ЭТО
  НЕВЕРНО, запись держится зачёркнутой намеренно.** Проверено экспериментом
  2026-08-04: сломали `proxy` (селектор на сервер с мёртвым портом) — резолв
  RU-доменов продолжил работать, `yandex.ru` ушёл в `direct` за 0.29 с. То есть
  сервер без детура и так прямой. Больше того, поставить `"detour": "direct"`
  НЕЛЬЗЯ: ядро падает на старте с `detour to an empty direct outbound makes no
  sense`, а `sing-box check` этого не ловит (возвращает 0).
  Ошибочная запись стоила половины разбора 4 августа: по ней строилась ложная
  версия про замкнутый круг, пока её не проверили замером.
- **Xmux-тюнинг убран, гипотеза закрыта отрицательно.** `maxConcurrency`/
  `cMaxReuseTimes`/`hMaxRequestTimes` не лечили обрывы, а усиливали их: они заставляют
  xray чаще переустанавливать xhttp-сессию, и каждое переподключение попадало в петлю
  выше. Мост с дефолтным xmux проверен отдельно через CLI — 3 МБ на ~4.7 МБ/с.

### Раздельное туннелирование (rule-based роутинг)
UI: выпадающий список «Маршрутизация» (`Весь трафик через VPN` / `Российские сайты —
напрямую`) + галочка «Блокировать рекламу и трекеры». Обе настройки в
SharedPreferences (`routing_mode`, `block_ads`), работают и в TUN, и в обычном режиме.

- Правила запекаются в конфиг ядра при старте. Через Clash API их, в отличие от
  выбора сервера, подменить нельзя — смена режима требует нажать «Запустить»
  заново. UI об этом честно пишет в лог (`_restartHint`).
- Наборы правил — бинарные `.srs` от SagerNet, качаются один раз в `rulesets/`
  рядом с .exe и подключаются как `"type": "local"`. **Не remote**: remote-набор
  sing-box тянет сам при каждом старте и падает целиком, если GitHub недоступен.
- **Тега `geosite-ru` не существует — 404.** Нужен `geosite-category-ru`. Плюс
  `geoip-ru` и `geosite-category-ads-all`. `geoip-private` тоже не существует —
  вместо него встроенное поле правила `ip_is_private: true`.
- Обязательна проверка размера скачанного: на несуществующий тег
  raw.githubusercontent отдаёт 14-байтную страничку «404: Not Found», и без
  проверки она легла бы на диск как валидный набор правил.
- Недокачанный набор — мягкая деградация: правило пропускается, трафик идёт
  через VPN целиком. Не стартовать туннель из-за недоступного GitHub — хуже.
- **Обновление наборов НЕ блокирует старт ядра.** Раньше `_ensureRuleSets`
  освежал устаревший набор прямо перед запуском, синхронно, с таймаутом 30 с
  на набор: со второго дня работы, если GitHub недоступен (то есть ровно
  тогда, когда VPN и нужен), подключение ждало до полутора минут на трёх
  наборах. Теперь `_refreshRuleSetsInBackground()` вызывается в `initState`
  без `await`, качает в `<файл>.new`, а `_applyPendingRuleSet` подменяет
  основной файл перед стартом ядра — когда его заведомо никто не читает
  (sing-box читает .srs при запуске, перезапись под ним была бы гонкой).
  Обновляются только наборы, уже лежащие на диске: качать список рекламы
  тому, кто её не блокирует, незачем. Проверено запуском: три `.new` легли
  за 25 с, geosite-category-ru реально обновился (8400 → 8537 Б), окно при
  этом открылось сразу.
- Путь «набора нет ни на диске, ни в комплекте» оставлен синхронным, но с
  таймаутом 10 с: стартовать без правила лучше, чем ждать минуту.
- **Порядок правил значим**, побеждает первое совпавшее: реклама режется ДО
  RU-обхода, иначе `ad.ozone.ru` как российский домен ушёл бы в `direct`.
- **DNS-блок задаётся в ОБОИХ режимах, не только в TUN.** В обычном его раньше не
  было вовсе — резолв шёл через системный. С включённым `geoip-ru` sing-box обязан
  резолвить КАЖДЫЙ домен, чтобы понять, российский ли адрес, и любая заминка
  системного резолвера вешала сразу весь трафик, а не отдельные сайты (симптом у
  пользователя: включил «РФ напрямую» + рекламу — перестали открываться YouTube,
  Telegram и вообще всё). Проверено запуском: ядро стартует за 0.03 с, YouTube/
  Telegram/Google идут через VPN, Яндекс и Mail.ru — напрямую.
- В TUN обязательно правило `{"action":"sniff"}` первым — TUN отдаёт роутеру
  голый IP, и без вынюхивания домена из TLS SNI доменные правила применять не к
  чему. В обычном режиме домен приходит прямо в SOCKS/HTTP-запросе, sniff не нужен.
- RU-домены резолвятся через `dns-direct`, иначе `geoip-ru` промахивается:
  зарубежный DNS для российского сайта вернёт не тот IP, что видит местный резолвер.
- Проверено в CLI (mixed-инбаунд, без TUN и UAC): `yandex.ru` → `outbound/direct`,
  `api.ipify.org` → `outbound/socks[proxy]` с exit-IP сервера, `ad.ozone.ru` → reset.

### Сценарий «вставил ссылку и забыл» — что должно работать само
Целевой сценарий: пользователь ставит приложение, вставляет ссылку подписки,
нажимает «Запустить» — и больше ничего не делает. Российские сайты идут
напрямую, остальное через VPN. Дефолты подобраны под это:

- `_routingMode` по умолчанию **`bypassRu`**, а не `global`. Дефолт задан в ДВУХ
  местах — у поля и в `orElse` при чтении из prefs (на свежей установке
  сохранённого значения ещё нет, и без второго места режим включался бы
  только со второго запуска).
- `autoConnectAfterLaunch = true`. Без профиля ничего не произойдёт —
  `_applyLaunchBehaviour` проверяет, что список серверов непустой.
- Автозапуск с системой **спрашивается один раз диалогом**, а не включается
  молча: запись в `HKCU\...\Run` — изменение системы, и антивирусы к
  незаявленным записям в Run относятся настороженно. Вопрос задаётся, только
  когда есть что запускать (`_servers.isNotEmpty`) — на самом первом старте
  человек ещё не понял, чем пользуется. Флаг `autostart_asked` в prefs.
  При `hideAfterLaunch` диалог пропускается БЕЗ установки флага: окно в трее,
  диалога никто не увидит — спросим при следующем видимом запуске.
- `_maybeAskAutostart` вызывается ПОСЛЕ автоподключения: диалог ждёт ответа
  человека, и держать из-за него поднятие VPN нельзя.
- Само собой уже работало: авто-выбор быстрейшего сервера при подключении,
  системный прокси, автообновление подписки, подъём упавшего ядра, трей.

### Настройки, трей, автозапуск
`AppSettings` — всё, что раньше было константами в `_writeConfig` (DNS, порт локального
прокси, доступ из локалки, порт Clash API, имя/адреса/стек/MTU/strict_route TUN) плюс
блок автоматики. Хранится в SharedPreferences одним JSON (`app_settings`). Дефолты
подобраны так, чтобы в точности повторять поведение до появления экрана настроек;
битый JSON молча откатывается на дефолты, а не роняет запуск.

- Трей на `tray_manager`, окно на `window_manager`. В `main()` обязателен
  `windowManager.setPreventClose(true)` — иначе крестик убивает процесс вместе с
  ядром, и «включил и забыл» не работает. Меню трея пересобирается
  (`_refreshTrayMenu`) на каждом изменении `_runningEngine`, иначе пункт
  «Подключить/Отключить» врёт.
- Иконка трея — `assets/tray_icon.ico`, копия `windows/runner/resources/app_icon.ico`,
  объявлена в `pubspec.yaml`. Ресурс, вкомпилированный в .exe, для трея не годится:
  плагину нужен файл.
- Автозапуск — запись в `HKCU\...\CurrentVersion\Run` через `reg add` (не HKLM:
  не нужны права администратора). Путь к .exe в кавычках, иначе пробелы ломают команду.
- `_applyLaunchBehaviour()` зовётся в конце `_loadProfiles`, а не в `initState` —
  автоподключению нужен уже разобранный список серверов.

### Два режима теста задержки
Настройка «Что мерить» (`AppSettings.latencyMode`):

- `proxy` — сквозной замер через пробное ядро до `latencyUrl`. Даёт **100–200 мс**.
- `connect` — только `Socket.connect` до сервера, без единого процесса. Даёт **10–40 мс**.

Это разные величины, а не «правильная и неправильная». Замерено на живом ядре:
сквозной путь до `gstatic` через VLESS-сервер — 122–202 мс, TCP-подключение
к тому же серверу — 10–27 мс. **Karing показывает 25–40 мс, то есть меряет путь
до сервера.** Отсюда и жалоба на «высокий пинг» у нас — мы честно мерили другое.

- Замена `https://` на `http://` в `latencyUrl` даёт выигрыш всего ~25%
  (186/180/122 против 198/188/202) — гипотеза, что дело в лишнем TLS, НЕ подтвердилась.
  `http` всё равно оставлен дефолтом: он и быстрее, и совпадает с дефолтом Clash/Karing.
- **Hysteria2 (и вообще QUIC/UDP-протоколы) режимом `connect` не измеряются в
  принципе** — их порт не принимает TCP-соединений. Проверено: `connect` к порту
  Hysteria2 падает мгновенно, к VLESS проходит за 0.1 с. Поэтому протоколы из
  `_udpOnlyProtocols` (`hysteria2`, `hysteria`, `tuic`) даже в режиме `connect`
  меряются через пробное ядро (проверено: 203/237 мс). Побочный эффект — в списке
  они показывают заметно большую цифру, чем соседи: величина другая, не задержка хуже.
- **Адрес проверки решает почти всё.** Замерено через один и тот же сервер:
  `www.gstatic.com` — 416 мс, `www.google.com` — 117 мс, `cp.cloudflare.com` — 82 мс.
  Cloudflare anycast отдаётся из дата-центра рядом с прокси-сервером, поэтому
  «второе плечо» (сервер → проверочный сайт) почти не попадает в замер.
  Дефолт — `https://cp.cloudflare.com/generate_204`.
- **URL обязан быть https.** Обычный HTTP через прокси Xray не держит соединение
  живым, и замерочный запрос, идущий по тому же `HttpClient` следом за
  прогревочным, падает с «Connection closed before full header was received» —
  все xhttp-серверы показывались недоступными. Проверено на живом ядре:
  http+прогрев — обрыв, http без прогрева — 436 мс, https+прогрев — 100 мс,
  https без прогрева — 350 мс. На всякий случай замер повторяется один раз
  на свежем соединении, если первая попытка упала.
- `connect` быстрый, но успех означает только сетевую доступность сервера —
  сломанный прокси таким тестом не ловится. В UI это подписано прямым текстом.
- Прогревочный запрос осмыслен только в Xray-ветке (там `HttpClient` переиспользует
  соединение). В sing-box-ветке Clash-эндпоинт `/delay` каждый раз открывает новое
  соединение, прогревать нечего — поэтому прогрев сделан отключаемым.

### Системный прокси (обычный режим)
Без него не-TUN режим бесполезен: ядро слушает `127.0.0.1:localPort`, но ни Windows,
ни браузер, ни Telegram про этот адрес не знают — трафик идёт мимо туннеля. Симптом
у пользователя выглядел как «IP поменялся, а сайт не открывается» (IP менял его
собственный v2rayN, не мы).

- **ГЛАВНОЕ: одной записи в реестр НЕДОСТАТОЧНО. Обязателен вызов WinINET**
  (`lib/system_proxy.dart`, `InternetSetOption` через FFI). `ProxyEnable`/
  `ProxyServer`/`ProxyOverride` в `Internet Settings` — это legacy-ЗЕРКАЛО.
  Действующую конфигурацию Windows держит бинарным блобом в
  `Internet Settings\Connections\DefaultConnectionSettings`, и именно её отдаёт
  `WinHttpGetIEProxyConfigForCurrentUser` браузерам и почти всему остальному.
  Windows синхронизирует зеркало с блобом только когда настройки меняют через
  API, а не `reg add`.
  **Как это выглядело (2026-08-04, живая машина):** приложение писало
  `ProxyEnable=1`, `ProxyServer=127.0.0.1:1337`, честно рапортовало в лог
  «System proxy enabled», sing-box поднимался за 0.08 с — и на порт 1337 не
  приходило НИ ОДНОГО соединения. Три подключения подряд в двух логах без
  единой строки `inbound connection`. Пользователь это описал как «включаю
  VPN, а он не работает».
  Доказательство снято чтением, без записи (`tools/check_system_proxy.dart`,
  `InternetQueryOptionW`): `FLAGS = 1` (`PROXY_TYPE_DIRECT`, «прямое
  подключение»), `PROXY_SERVER = 127.0.0.1:10808` — чужой адрес от v2rayN.
  То есть Windows всё это время считала подключение прямым.
  Ставим `PROXY_TYPE_DIRECT | PROXY_TYPE_PROXY` (3) и следом обязательные
  `INTERNET_OPTION_SETTINGS_CHANGED` + `INTERNET_OPTION_REFRESH` — без них
  изменение видят только процессы, запущенные ПОСЛЕ (в логе это была
  34-секундная пауза между «прокси включён» и первым соединением).
  Раскладка нативных структур считается от `sizeOf<IntPtr>()`, не прибита к
  x64. Ошибка в ней не падает, а молча ничего не делает — то есть выглядит
  ровно как исходный баг; поэтому она проверена чтением реальных значений.
- **PAC-скрипт (`AutoConfigURL`) имеет приоритет над фиксированным адресом.**
  Пока он стоит, наш прокси не действует вообще. Снимаем его на время сеанса
  и обязаны вернуть — иначе тихо ломаем человеку корпоративную сеть. Лежит
  в резерве вместе с остальным (`pac`).
- `_enableSystemProxy()` / `_restoreSystemProxy()` — ветка `HKCU\...\Internet Settings`,
  значения `ProxyEnable`/`ProxyServer`/`ProxyOverride`/`AutoConfigURL` через
  `reg add`/`reg query` (зеркало для окна системных настроек) ПЛЮС `WinInetProxy`.
- **Пустое значение при возврате УДАЛЯЕМ, а не пропускаем.** Раньше
  `if (server.isNotEmpty)` оставлял наш `127.0.0.1:1337` в системе навсегда у
  тех, у кого своего прокси не было. Стоило потом чему угодно выставить
  `ProxyEnable=1` — интернет ложился во всех программах разом, на мёртвый порт.
- **`<-loopback>` в списке исключений — ЛОВУШКА, читается наоборот.** Токен
  выглядит как «исключить петлю», а минус в нём ОТМЕНЯЕТ встроенное правило
  Windows «localhost мимо прокси» и загоняет петлевой трафик В ТУННЕЛЬ. Это
  то, что добавляют, когда петлю надо ПЕРЕХВАТИТЬ (снифферы). Стоял первым
  в дефолтном списке.
  Пока системный прокси фактически не включался, строка лежала мёртвым
  грузом. Как только включение заработало (см. WinINET выше), она ожила — и
  через туннель пошло общение программ с их же локальными службами. Наружу
  вышло как «Authentication failed / Sign in again» в Claude Code: сеть при
  этом исправна, что доказано дифференциальным замером — `api.anthropic.com`
  отдаёт побайтово одинаковый ответ через туннель и мимо него (401
  `invalid x-api-key`, тот же Cloudflare-эдж `-ARN`).
  **Урок:** правку, которая «включает» давно написанную настройку, надо
  перечитывать целиком. Список исключений годами не применялся ни разу, и
  ошибка в нём не могла проявиться.
- **IPv6-петлю (`::1`, `[::1]`) в список писать НЕЛЬЗЯ.** Казалось логичным
  дополнением к `127.*` — на деле WinINET такой записи не принимает и
  отвергает **весь набор опций целиком**: `InternetSetOption` возвращает
  отказ, прокси не включается вообще. Отдельные записи для петли и не нужны:
  как только из списка убран `<-loopback>`, Windows освобождает петлю сама, в
  обоих семействах адресов.
  **Симптом, по которому это узнаётся:** «Chrome работает, а остальное нет».
  Chromium читает плоские значения реестра сам, поэтому браузер уходит в
  туннель (15 МБ трафика, 45 соединений), а всё, что спрашивает WinINET,
  остаётся на прямом подключении.
- **Ничего «заодно» в дефолтный список не добавлять.** Отказ WinINET
  молчаливый и валит функцию целиком, поэтому цена лишней записи —
  неработающий VPN, а выгода — почти никакая. Правка списка должна отличаться
  от заведомо рабочей версии минимальным числом пунктов.
- **Обратное чтение обязательно** (`WinInetProxy.current()` после
  `enable()`). «Вызов вернул успех» и «система переключилась» — разные
  утверждения. Пока лог верил вызову на слово, он писал «прокси включён»,
  когда Windows оставалась на прямом подключении, и на поиск расхождения ушёл
  целый раунд отладки.
- **`GetLastError` читать только при `isLeaf: true`.** Без этого Dart успевает
  сделать своё между вызовом и чтением кода, и приезжает `GetLastError=0` —
  отказ выглядит беспричинным.
- **Если список исключений не принят — включаемся без него** (`bypassDropped`,
  вторая попытка с пустым bypass). Без исключений через туннель пойдёт
  локальная сеть — неприятно; без прокси не работает НИЧЕГО, при этом UI
  показывает «подключено». Второе несоразмерно хуже, поэтому деградируем и
  пишем об этом в лог.
- **В списке исключений нельзя сокращать маски.** Было `172.2*` — WinINET
  сравнивает ТЕКСТОМ, и эта маска ловила не только частные 172.20–172.29, но и
  публичные 172.2xx: `172.217.*` и `172.253.*` (Google/YouTube), `172.224.*`
  (Akamai). Всё, к чему обращались по голому IP оттуда, уходило мимо туннеля.
  Каждая восьмёрка выписана отдельно; старая маска чинится при чтении настроек
  (`_expandLegacy172Mask`) — у всех пользователей список уже сохранён, смена
  дефолта сама по себе ничего не лечит.
- **Прежнее значение обязательно сохраняется и возвращается** при остановке ядра И
  при выходе из приложения. Если оставить `ProxyEnable=1` с нашим мёртвым портом,
  интернет отвалится во ВСЕХ приложениях, и чинить это будут перезагрузкой, не
  понимая причины. У пользователя стоит `ProxyServer=127.0.0.1:3067` от v2rayN —
  затереть его нельзя.
- Разбор `reg query` проверен на живом выводе: `REG_\w+\s+(\S.*)$` корректно берёт
  и `0x0`, и строку с `;`/`*`/`<>`. Цикл «сохранить → подменить → вернуть» проверен
  на отдельном ключе `HKCU\Software\MultikSilaSelfTest`, состояние восстанавливается
  побайтово.
- В TUN-режиме системный прокси НЕ трогается — там маршрутизация идёт через адаптер.
- **Резерв лежит в SharedPreferences (`system_proxy_backup`), а не в памяти.** Память
  умирает вместе с процессом: при падении или снятии через Диспетчер задач
  восстановление не отрабатывало, прежние значения терялись, и система оставалась с
  `ProxyEnable=1` на мёртвый порт — интернет ложился во всех программах разом.
  Пользователь дважды чинил это перезагрузкой (после неё v2rayN при старте
  прописывает прокси на себя), не понимая причины.
- `_recoverSystemProxyIfNeeded()` в `initState`: если резерв на месте — прошлый сеанс
  умер ненормально, возвращаем прокси сразу при запуске. Резерв снимается только
  ПОСЛЕ попытки восстановления, иначе при сбое настоящие значения теряются навсегда.
  Повторный `_enableSystemProxy` не перезаписывает уже существующий резерв.
- Проверено end-to-end: подменили `ProxyServer` на наш порт при `ProxyEnable=0`
  (чтобы не рвать живой трафик), запустили приложение — оно записало в лог
  «прошлый сеанс не завершился штатно», вернуло `127.0.0.1:10808` и сняло резерв.

### Наборы правил вшиты в приложение
`assets/rulesets/*.srs` (66 КБ на три файла) бандлятся в сборку. `_ensureRuleSets`
сначала берёт их из комплекта через `rootBundle` и только потом лезет в сеть.
GitHub может быть недоступен ровно тогда, когда VPN нужнее всего, а тихий провал
скачивания вырождает режим «РФ напрямую» в «всё через VPN» без объяснений.

### Свои правила маршрутизации
Три списка в `AppSettings` (`customDirect` / `customProxy` / `customBlock`), по записи
в строке: домен или IP. Экран — кнопка «Свои правила» рядом с блокировкой рекламы.

- Домены кладутся в `domain_suffix`, а не `domain`: запись `example.com` должна ловить
  и поддомены, иначе пользователю пришлось бы перечислять их руками.
- Голому IP дописывается `/32` (IPv6 — `/128`), sing-box ждёт CIDR.
- **Личные списки идут ВЫШЕ готовых наборов** в `route.rules`, иначе режим
  «РФ напрямую» перебивал бы явный выбор. Проверено запуском: `mail.ru` (российский)
  в списке «через VPN» ушёл в `srv_11`, `github.com` в списке «напрямую» — в `direct`.
- Домены из `customDirect` дублируются в `dns.rules` на `dns-direct`: без этого сайт
  идёт мимо туннеля, а DNS-запрос о нём — через туннель.

### Экран «Конфиги ядер» (в диагностике, иконка в шапке)
Показывает как есть все конфиги, которые приложение отдало ядрам:
`config.json`, `xray_config.json` и все `xray_bridge_*.json` (мосты в TUN
поднимаются по файлу на сервер, поэтому список строится сканированием
каталога). Без разбора и интерпретации — вопрос «почему трафик пошёл не
туда» решается чтением `route.rules`, и любая наша трактовка тут только
добавила бы шанс соврать. Есть копирование в буфер. Горизонтальная прокрутка
обязательна: строки JSON длинные, перенос ломает читаемость.

### Экран «Интерфейсы и маршруты» (в диагностике, иконка в шапке)
Сделан ровно под ту беду, на которой сгорел прогон TUN 2026-07-31: за маршрут
по умолчанию борются несколько адаптеров. Показывает маршруты `0.0.0.0/0` с
метриками и шлюзами (побеждает наименьшая), список интерфейсов с метриками,
состоянием и адресами, и КРАСНУЮ карточку, если минимальную метрику делят
несколько адаптеров.

- Проверено на живой машине: видно два маршрута с метрикой 0 — `Беспроводная
  сеть` (шлюз <шлюз локальной сети>) и `xray_tun` от v2rayN. Ровно то состояние, из-за
  которого чистый тест TUN невозможен.
- Данные берутся одним вызовом PowerShell (`Get-NetRoute` + `Get-NetIPInterface`
  → JSON), адреса — средствами Dart (`NetworkInterface.list`).
- **`[Console]::OutputEncoding = [Text.Encoding]::UTF8` в скрипте обязателен**,
  плюс `stdoutEncoding: utf8` в `Process.run`: без этого PS 5.1 отдаёт
  консольную кодировку и «Беспроводная сеть» приезжает мусором.

### Импорт из QR-кода (картинкой, не камерой)
Камеры у Windows-приложения нет (и плагина под неё тоже), зато картинка с
кодом есть всегда: скриншот с телефона, фото, сохранённое из чата. Файл
читается через `image` + `zxing2` вручную: zxing2 ждёт линейный массив
ARGB-пикселей, а не объект картинки. Содержимое различается по схеме —
`http(s)://` заводит обычный профиль-подписку, остальное кладётся локальным
профилем. Проверено полным кругом в CLI (генерация тем же `qr`, на котором
построен `qr_flutter`, → чтение кодом из `_importProfileFromQr`): ссылка
сервера, ссылка подписки и многострочный список серверов — 3 из 3 верно,
пустая картинка корректно отвергается `NotFoundException`.

### Экран «О программе»
Версии приложения и ОБОИХ ядер (спрашиваются у бинарников — единственный
честный источник, см. историю с pre-release Xray), пути к папке и логу,
ручная проверка обновлений ядер. `kAppVersion` — константа в main.dart,
менять ВМЕСТЕ с `version:` в pubspec.yaml, автоматически они не связаны.
Если версия ядра не читается, экран прямо об этом пишет: иначе человек ждёт
автообновлений, которых для этого ядра никогда не будет.

### `route.default_domain_resolver` — обязателен, иначе свежие ядра НЕ СТАРТУЮТ
Чем резолвить домены из полей подключения (адрес сервера у outbound). В
sing-box 1.12 отсутствие ключа было депрекейтом, а **1.13.16 уже отказывается
запускаться**: `to continuing using this feature, set
ENABLE_DEPRECATED_MISSING_DOMAIN_RESOLVER=true`. Ставим `"dns-direct"`, а не
`dns-remote`: адрес прокси-сервера надо узнавать мимо туннеля.

Поймано при проверке кандидата на автообновление: с ядром, лежащим у нас,
конфиг работал, а новое падало на нём намертво. Ключ принимают ОБА ядра —
проверено `check` и реальным запуском (yandex → direct, Google → через прокси,
ошибок ноль у обоих).

**Отсюда усиление автообновления:** мало проверить, что скачанный бинарь
запускается и называет версию — он обязан ПРИНЯТЬ наш `config.json`
(`check -c`). Иначе автообновление тихо заменило бы рабочее ядро на такое,
с которым приложение перестаёт подключаться.

### Автообновление ядер (`autoUpdateCores`, по умолчанию включено)
Качает свежие sing-box/Xray с GitHub, кладёт рядом как `<файл>.exe.new` и
подменяет при следующем старте приложения (`_applyPendingCores` в начале
`_loadProfiles`, до автоподключения) — работающий .exe Windows заменить не даст.

- **Версию спрашиваем у самого бинаря, а не помним тег.** У пользователя стоял
  Xray **26.7.28**, а `/releases/latest` отдаёт последний СТАБИЛЬНЫЙ — 26.3.27:
  все свежие релизы Xray помечены pre-release. Обновление «по отличию тега»
  откатило бы рабочее ядро назад.
- **Разбор версии строго после имени ядра**: `(?:sing-box version|Xray)\s+(x.y.z)`.
  Наивное «первое число вида x.y.z» ловит версию Go — старый sing-box печатает
  `sing-box version unknown`, а следом `Environment: go1.26.5`, и неизвестная
  версия ядра выдавалась бы за известную.
- **Сравнение по числам, а не строкой**: `1.9.0` строкой больше `1.13.15`.
- Версия не читается — ядро НЕ трогаем. Лежащий в проекте sing-box собран без
  версии (`version unknown`), поэтому автообновление его не тронет, пока туда
  один раз не положат официальный релиз.
- Скачанный файл обязан запуститься и назвать версию выше установленной, иначе
  `.new` удаляется. Битую сборку лучше выбросить сразу, чем узнать о ней по
  тому, что приложение перестало подключаться.
- Ассет выбирается строго: `-windows-amd64.zip` без `legacy` (в релизе рядом
  лежат 386, arm64 и сборка для Windows 7) и ровно `Xray-windows-64.zip`.
- В архиве sing-box .exe лежит в подпапке `sing-box-<ver>-windows-amd64/`,
  у Xray — в корне; поэтому ищем по имени файла, а не по полному пути.
- `libcronet.dll` из архива sing-box НЕ берём: проверено запуском — ядро
  1.13.15 без неё стартует и отдаёт HTTP 204.
- Логика проверена отдельным Dart-скриптом на живых бинарниках и настоящих
  архивах: разбор версий, сравнение (включая случай отката), извлечение из zip,
  выбор ассета среди пяти windows-сборок.

### Правила для программ (per-app)
`AppSettings.appRules`: полный путь к .exe -> `proxy` | `direct` | `block`.
Экран — кнопка «Правила для программ» на вкладке маршрутизации.

- **Путь, а не имя процесса.** Под одним именем в системе легко живут разные
  программы (у пользователя свой `xray.exe` от v2rayN), и правило по имени
  молча зацепило бы чужое — та же грабля, что с `_killStrayOnOurPorts`.
- **Работает и БЕЗ TUN.** Проверено запуском с контролем: правило
  `process_path` на `C:\Program Files\Git\mingw64\bin\curl.exe` с действием
  `reject` уронило именно его (`http=000`), а `C:\WINDOWS\system32\curl.exe`
  в том же ядре отдал 204. Второй заход с действием `direct`: целевой бинарь
  ушёл в `outbound/direct[direct]`, контрольный — в `outbound/vless[srv_0]`.
  То есть sing-box определяет процесс-владельца и для соединений через
  mixed-инбаунд, не только для голых пакетов из TUN.
- Правила собираются по ОДНОМУ на действие (все пути в один `process_path`),
  а не по правилу на программу: список правил перебирается на каждое
  соединение. Несуществующий путь в списке ничему не мешает — проверено.
- В `route.rules` стоят выше личных списков и наборов: «эта программа —
  всегда так» это самое конкретное указание, какое пользователь может дать.
- Список запущенных программ грузится ПО КНОПКЕ, а не при открытии экрана:
  `Get-CimInstance Win32_Process` занимает около секунды. Из неэлевированной
  сессии у чужих процессов `ExecutablePath` пуст — они отсеиваются сами.

### Экран активных соединений
Clash API `/connections`, опрос раз в 1.5 с. Формат ответа (проверен на живом ядре):
`chains` (первый элемент — реально использованный outbound, дальше селекторы),
`rule` + `rulePayload` (какое правило сработало), `metadata.host`/`destinationIP`/
`network`/`destinationPort`, `upload`/`download`, `start`.
Долгое нажатие рвёт соединение, кнопка в шапке — все сразу
(`DELETE /connections/{id}` и `DELETE /connections`, оба отдают 204 — проверено).
Теги `srv_N` подменяются именами серверов. **Работает только с ядром sing-box** —
у Xray Clash API нет вообще.

### NTP, раздельные GeoSite/GeoIP, режим IPv6, QR, статистика
- **NTP — БЕЗ `detour`.** Reality и VMess рвут соединение при расхождении
  часов. Первая версия ставила `"detour": "direct"` (казалось логичным —
  за временем идти мимо туннеля): ядро пишет `ntp: initialize time: detour
  to an empty direct outbound makes no sense`, NTP молча не работает, а сам
  прокси при этом живёт. Ровно та же ловушка, что с `dns-direct`, и
  `sing-box check` её опять НЕ ловит. A/B с контролем: без ntp — HTTP 204;
  с detour — 204, но ERROR и никакой сверки; без detour — 204 и
  `ntp: updated time` в логе. Хост NTP добавляется в `bypassDomains`
  (резолв через `dns-direct`).
- **GeoIP без `{"action":"resolve"}` в обычном режиме не работает вообще.**
  Соединение приходит доменом (браузер отдаёт хост прямо в SOCKS/HTTP), и
  правило по IP к нему не применяется. Проверено: с одним лишь `geoip-ru`
  `yandex.ru` и `mail.ru` уходили в прокси, хотя набор загружен; с `resolve`
  перед правилом оба ушли в `direct`. В TUN резолв не нужен — там адрес уже
  голый, поэтому `needsResolve = !_tunMode && geoIpReady`. Правило стоит
  ПОСЛЕ доменных (личные списки, сервисы, реклама): им резолв ни к чему.
- **Набор geosite качается и когда роутинг по нему выключен**, если включён
  geoip: по нему строится DNS-правило «RU-домены резолвим местным
  резолвером». Без него geoip промахивается — зарубежный DNS на российский
  сайт отдаёт не тот адрес. Отсюда `wantGeoSite` (роутинг) отдельно от
  `geoSiteReady` (файл на диске).
- **Режим IPv6** — это `dnsStrategy` с человеческими подписями
  (Выключен / Включён, сначала IPv4 / Включён, сначала IPv6 / Только IPv6).
  Перехват IPv6 адаптером TUN оставлен ОТДЕЛЬНЫМ переключателем, хотя Karing
  сводит всё в одну настройку: комбинация «`ipv4_only` + TUN ловит IPv6»
  осмысленна (не отдаём AAAA, но страхуемся, если адрес добыт мимо нашего DNS).
- **QR-коды** — `qr_flutter`. Долгое нажатие на сервере в списке и кнопка у
  профиля. Исходная ссылка хранится в `ParsedServer.link`, заполняется в
  ОДНОМ месте после разбора строки, а не в семи ветках парсеров. Код рисуется
  на белом поле всегда, даже в тёмной теме: сканеры телефонов ждут тёмный
  узор на светлом, инверсия читается через раз. У локального профиля
  (`file:`) кнопка выключена — на другом устройстве этого файла нет.
- **Статистика** — свой опрос `/connections` раз в секунду, скорость как
  разница накопленных счётчиков. Проверено: после скачивания 3 МБ
  `downloadTotal` = 3 010 366. Отрицательная разница (ядро перезапустили и
  счётчики обнулились) считается нулём, иначе график уходит в минус.
  График — свой `CustomPainter`, обе ломаные в общем масштабе по максимуму:
  иначе отдача, обычно на порядок меньше, вырождается в прямую по низу.

### Данные подписки и автообновление
Панель отдаёт их в заголовках ответа (проверено на живой подписке):
```
Subscription-Userinfo: upload=..; download=..; total=0; expire=0
Profile-Update-Interval: 12
```
- `total=0` — безлимит, `expire=0` — бессрочно. Полосу остатка и срок показываем
  ТОЛЬКО при ненулевых значениях: рисовать «осталось 0 Б» на безлимитном тарифе —
  враньё. У пользователя как раз безлимит, израсходовано ~464 ГБ.
- Разбор по именам полей, а не по позиции: набор и порядок у панелей разный.
- Интервал автообновления берётся из `Profile-Update-Interval` (у пользователя 12 ч) —
  панель лучше знает, как часто её опрашивать. Переключатель в настройках.
- Поля сохраняются в профиле (`SubscriptionProfile`), поэтому цифры видны сразу
  при запуске, до первого обновления.

### Темы и импорт профилей
- Тема хранится в глобальном `ValueNotifier<ThemeMode> appThemeMode`, а не в
  состоянии страницы: `MaterialApp` стоит ВЫШЕ `CoreControlPage`, и иначе
  переключение из настроек не дошло бы до него без перезапуска приложения.
  Варианты: тёмная (по умолчанию), светлая, как в системе.
- Профиль можно завести тремя способами (меню на кнопке «+»): по ссылке,
  из файла (`file_selector`), вставкой содержимого.
- **Профиль без ссылки хранит содержимое файлом рядом с .exe
  (`profile_<id>.txt`), а в `url` кладёт путь со схемой `file:`.** Так загрузка,
  обновление и переключение работают с ним ровно как с обычной подпиской, без
  отдельной ветки в коде. `_loadSubscription` разветвляется только в одном месте.
- Разбор содержимого вынесен в `_applySubscriptionContent` — общий для сетевой
  загрузки и локального файла.

### КРИТИЧНО: киллеры расстреливали собственные мосты (исправлено 2026-08-03)
Симптом из живого лога пользователя:
```
16:02:24.199 Мост Xray для <xhttp-сервер 3> готов на порту 1338
...
16:02:25.701 Мост Xray для <xhttp-сервер> готов на порту 1342
16:02:25.942 Убрал зависший процесс на нашем порту (PID 23356)
16:02:26.746 Убрал зависший процесс на нашем порту (PID 12416)
```
Пять мостов подняты — пять тут же убиты. Причина: в TUN `_startCore` сначала
зовёт `_ensureAllXrayBridgesRunning()` (порты 1338+), а `_startSingboxCore`
следом — `_killStrayOnOurPorts()`, который честно находит владельцев НАШИХ
портов и бьёт их, не отличая чужой мусор от своих секундной давности.
`_killOurProcessesByPath` имел ту же дыру: мосты запускаются ТЕМ ЖЕ
`xray.exe` из нашей папки.

**Наружу баг выходил не сразу** — пока активен singbox-сервер, мосты не нужны.
Ломалось при переключении на любой xhttp-сервер: каждое соединение падало с
`dial tcp 127.0.0.1:134x: connectex: No connection could be made`. В логе так
легли 8 запросов к Telegram и Microsoft после переключения на <xhttp-сервер>.

**Лечение:** обе функции получили список PID своих живых процессов
(`_xrayBridgeProcesses`, `_coreProcess`, `_xrayProcess`) и пропускают их.
Защита по PID, а не порядком вызовов: порядок легко нарушить следующей правкой.

**Проверено после фикса (2026-08-03, живое приложение под TUN):** все пять
мостов отвечают напрямую по SOCKS5 — HTTP 204 за 0.17–0.24 с (порты
1338 <xhttp-сервер 3>, 1339 <xhttp-сервер 4>, 1340 <xhttp-сервер 5>, 1341 <xhttp-сервер 2>, 1342 <xhttp-сервер>).
Сквозной путь тоже: переключение selector'а на `srv_13` (<xhttp-сервер>, xhttp
через мост) дало 204 за 0.166 с и 2 МБ за 0.368 с — раньше на этом месте
сыпалось `connection refused`. После проверки selector возвращён на
исходный `srv_8`. Теги назначаются по порядку в подписке: srv_0 VLESS,
srv_1 <сервер A>, srv_2 <xhttp-сервер 3>, srv_3 <xhttp-сервер 4>, srv_4 VLESS GRPC, srv_5
Hist, srv_6 <сервер C>, srv_7 <xhttp-сервер 5>, srv_8 <сервер D>, srv_9 Trojan T,
srv_10 Trojan R, srv_11 <сервер B>, srv_12 <xhttp-сервер 2>, srv_13 <xhttp-сервер>.

**Плюс мост больше не считается живым по наличию объекта в словаре.** Раньше
`_ensureXrayBridge` начинался с `if (existing != null) return`, и умерший мост
навсегда оставался «поднятым» — подстраховка при переключении молча не
срабатывала. Теперь спрашивается ПОРТ, а на `process.exitCode` повешен
обработчик: смерть моста убирает его из словаря и пишется в лог. Проверено
отдельно: сам по себе мост живёт стабильно (98 с, все запросы 204) — падал он
исключительно от наших же киллеров.

### Защита «своих» PID работала против нас при рестарте (исправлено 2026-08-04)
Оба киллера пропускают PID'ы из `_coreProcess`/`_xrayProcess`/
`_xrayBridgeProcesses` — иначе они расстреливали бы собственные мосты (см.
раздел выше). Но `_startSingboxCore`/`_startXrayCore` звали их ДО того, как
обнулить ссылки, и пока ссылка указывала на ещё живое СТАРОЕ ядро, оно
оказывалось защищённым от уборки: сидело на 1337, Clash API и адаптере
`SilaTUN`, новое ядро на них не вставало и умирало, а UI при этом рапортовал
«подключено» — трафик продолжал идти через прежний сервер.

Путь наружу: `_switchServer` зовёт `_startCore` **без остановки** — то есть при
любой смене движка (xhttp ↔ sing-box в обычном режиме) и при недоступном
Clash API. Лечение: `kill()` предыдущего ядра по хендлу и обнуление ссылок
ПЕРЕД киллерами.

### Добивание своих процессов по пути (`_killOurProcessesByPath`)
Порт спасает не всегда: sing-box в TUN держит адаптер `SilaTUN`, и если прошлый
экземпляр жив, новый падает с `configure tun interface: Cannot create a file
when that file already exists` — а Clash API он занять не успел, по портам не найти.
Ищем через `Get-CimInstance Win32_Process` процессы с **точно нашим**
`ExecutablePath` и бьём по PID. Безопасно: у v2rayN путь другой, а из
неэлевированной сессии его `ExecutablePath` вообще пустой — совпадения не будет.

### Включение прокси РВЁТ живые соединения — это норма, а не баг

### Адрес сервера ЗАПЕКАЕТСЯ в конфиг — иначе TUN не работает вовсе
Самая упрямая поломка дня: с включённым TUN не открывался ни один сайт при
полностью исправном туннеле. Ядро на уровне `debug` (уровень `info` про это
молчит!) сказало прямо:

```
dns: lookup domain fill.mrmultik.shop
dns: lookup failed for fill.mrmultik.shop: context deadline exceeded   (10.0 с)
```

Круг: чтобы поднять прокси, нужен адрес его хоста → чтобы узнать адрес, нужен
DNS → DNS ходит только через прокси. Десять секунд на попытку, и так на каждое
соединение.

**Выбором резолвера это НЕ лечится, проверены оба варианта:**
- публичный адрес (1.1.1.1) под TUN уходит по физическому каналу, и у
  провайдера он может быть закрыт;
- системный резолвер (`"type": "local"`) сам ходит через туннель и попадает в
  тот же круг. Промежуточная правка с ним оставлена — она верна сама по себе
  (так же делает Karing) и стоит на `default_domain_resolver`, — но проблему
  решала не она.

**Лечение — `_bakeServerIps`: не резолвить в рантайме вообще.** Адрес известен
на этапе генерации конфига, когда туннеля ещё нет и сеть обычная. В
`outbound.server` кладётся готовый IP.

- **Имя хоста обязано попасть в `tls.server_name`** до подмены. Иначе сервер
  видит рукопожатие без SNI и рвёт соединение.
- **Порядок в `_writeConfig` значим дважды:** имена собираются для DNS-правил
  ДО подмены (иначе правило «хосты серверов резолвим напрямую» строится из
  IP-литералов), а сама подмена — ДО сборки `config["outbounds"]` (там значения
  копируются в конфиг, и правка после этой строки в JSON не попадёт; на это я
  наступил).
- Не удалось отрезолвить — оставляем имя: пусть ядро попробует само.

Проверено живьём: в конфиге `78.17.99.116` с правильным SNI у каждого сервера,
ошибок резолва в логе ноль, DNS-обмен **68 мс** вместо 10 000 мс таймаута.

**Методический вывод (третий за день, тот же самый):** уровень `info` показывает,
что пакет ушёл, но не почему нет ответа. Один запуск с `log.level: debug`
(`tools/tun_debug_run.ps1`) дал ответ за минуту после часа гипотез.

### Почему режим замера `connect` не годится по умолчанию
Все 14 серверов подписки живут на ОДНОМ хосте и отличаются портом. TCP-рукопожатие
до хоста одинаковое, поэтому `connect` показывает всем одну цифру — выбирать не из
чего. Дефолт вернули на `proxy`: он идёт через сам протокол и различает серверы.

### Mux — реализован, но на этой подписке ЛОМАЕТ соединение
`multiplex` в sing-box поддерживается (проверены h2mux/smux/yamux, padding, brutal —
все проходят `check`). Но мультиплексирование требует поддержки на СТОРОНЕ СЕРВЕРА.
Чистый A/B на одном и том же Trojan-сервере, все три протокола:
контроль без Mux — HTTP 204 за 0.35 с; h2mux, smux, yamux — обрыв во всех трёх.
То есть дело не в выборе протокола: сервер провайдера мультиплексирование не
поддерживает вообще. Со стороны клиента это не чинится — Mux согласованный,
сервер обязан распаковывать потоки. Включается настройкой НА СЕРВЕРЕ.
Поэтому по умолчанию выключен, а в UI написан результат замера.

**Урок по методике:** первые два захода дали ложный результат, потому что контроль
не проверялся. Сначала тестировал на `<сервер A>` (порт 25025) — упал и с Mux, и без,
сервер был просто мёртв. Потом убрал `flow: xtls-rprx-vision` у REALITY-сервера,
чтобы Mux стал применим, — и упало из-за отсутствия flow, а не из-за Mux.
**Контроль обязателен в каждом A/B: без него измеряется что угодно, кроме цели.**

Mux не применяется к outbound'ам с `flow: xtls-rprx-vision` — Vision сам управляет
потоком (`_applyMux` их пропускает).

### DNS: FakeIP подключается ПРАВИЛОМ, а не через final
`"final": "dns-fake"` роняет ядро: `default server cannot be fakeip`. Правильно —
последним правилом `{"query_type":["A","AAAA"],"server":"dns-fake"}`, уже после
всех правил честного резолва. Порядок принципиален: обход РФ работает по geoip,
то есть сравнивает НАСТОЯЩИЕ адреса, и если бы российские домены получали
выдуманный адрес, правило промахивалось бы всегда. Настоящий адрес гарантированно
получают: домены прокси-серверов, RU-домены, личные списки «напрямую» и сервисы,
помеченные «напрямую». При FakeIP обязателен `independent_cache`.

Проверено на нашей сборке: `fakeip`, `hosts` (статические записи), `client_subnet`
(ECS), `rewrite_ttl`, `independent_cache`, `action: hijack-dns` — всё поддерживается.

### NTP — сверка времени ядром
Настройка «NTP» (`ntpEnabled`/`ntpServer`/`ntpPort`/`ntpInterval`). Reality и VMess
рвут соединение при расхождении часов больше пары минут; sing-box держит своё

- A/B с контролем (обязателен): без ntp — HTTP 204; с detour — HTTP 204, но

### Раздельные переключатели наборов правил (GeoSite / GeoIP / ACL)
Секция настроек «Наборы правил»: `geoSiteEnabled`, `geoIpEnabled`. ACL (реклама)
остался галочкой `_blockAds` на главном экране — он не зависит от режима
маршрутизации.

- **GeoIP в обычном (не-TUN) режиме без `{"action":"resolve"}` не работает
  вообще.** Соединение приходит доменом (браузер отдаёт хост прямо в SOCKS/
  HTTP-запросе), и правило по IP к нему не применяется. Проверено запуском:
  только geoip-ru — `yandex.ru` и `mail.ru` ушли в прокси, хотя набор загружен;
  с `resolve` перед правилом оба ушли в `direct`. В TUN resolve не нужен —
  туда соединение приходит уже голым адресом, поэтому правило добавляется
  только при `!_tunMode`.
- Промежуточная гипотеза «хватит DNS-правила `geosite → dns-direct`» проверена
  и НЕ подтвердилась: без resolve адрес всё равно не с чем сравнивать.
- `resolve` стоит НИЖЕ доменных правил (личные списки, сервисы, реклама) —
  всё, что решается по домену, до резолва уже разобрано.
- Набор geosite скачивается и когда роутинг по нему выключен, а geoip включён:
  по нему строится DNS-правило «RU-домены резолвим местным резолвером», без
  которого geoip промахивается (зарубежный DNS отдаёт другой адрес).

### Режим IPv6
Тот же `dnsStrategy` (4 значения sing-box), но подписан по-человечески:

разделе про TUN.

### Экран статистики
Кнопка-график в шапке. Скорость ↓/↑ в реальном времени, график за последнюю

### Логирование
`app_log.txt` рядом с .exe — дублирует весь UI-лог на диск с флашем на каждой строке,
переживает даже жёсткий килл через Диспетчер задач. Файл перезаписывается заново при
каждом запуске приложения (`FileMode.write` в initState, дальше `FileMode.append`).
Все места, где раньше был `setState(() => _log += ...)`, теперь идут через
`_appendLog()`/`_resetLog()` — если добавляешь новый лог, используй эти хелперы, а не
пиши в `_log` напрямую, иначе новая запись не попадёт в файл (уже наступали на это с
"Тест задержки" — кнопка ничего не писала в файл, пока не завели явное логирование).

### Профили подписок
`SubscriptionProfile` (id/name/url), список хранится в SharedPreferences как JSON.
Автомиграция со старой однопрофильной схемы (`subscription_url`). Кэш серверов на
профиль в памяти (`_serverCache`).

### Форматы подписок: ссылки, Clash YAML, конфиг sing-box
Формат определяется по СОДЕРЖИМОМУ (`_applySubscriptionContent`), а не по
расширению: подписка приходит по ссылке, где расширения нет вовсе.
`{`/`[` в начале → sing-box JSON, `^proxies:` → Clash YAML, иначе построчный
разбор ссылок (vless/vmess/trojan/hysteria2/**ss**).

- **Раньше Clash-подписка выглядела как сломанная.** Ни одна её строка не
  начинается с известной схемы, поэтому получалось «Распознано: 0 —
  пропущено: 340»: по этой строке невозможно понять, что формат просто другой.
  При нуле распознанных теперь пишется прямо, какие форматы понимаем
  (`sub.unknownFormat`). Хуже того, выбор файла профиля УЖЕ предлагал
  `yaml`/`json` — то есть приложение приглашало выбрать то, чего не умело.
- **Clash — это перевод, а не переименование полей.** `cipher` → `method`,
  `alterId` → `alter_id`, `servername`/`sni`/`peer` → `tls.server_name`,
  `skip-cert-verify` → `tls.insecure`, `client-fingerprint` → `tls.utls`,
  `reality-opts.public-key` → `tls.reality.public_key`,
  `grpc-opts.grpc-service-name` → `transport.service_name`.
- **У trojan/hysteria2/tuic ключа `tls:` в Clash-записи обычно НЕТ** — TLS у них
  часть протокола. Без принудительного включения (`force` в `_clashTls`) они
  собирались бы без TLS и молча не подключались.
- `network: tcp` транспорта НЕ добавляет: в sing-box это умолчание, отдельного
  блока для него не существует.
- Незнакомый тип (`ssr`, `snell`, `wireguard`) пропускается молча — одна
  чужая запись не повод терять остальные 300.
- **`ss://` живёт в двух несовместимых формах одновременно**: SIP002
  (`base64(method:password)@host:port`) и старая, где в base64 упаковано всё
  целиком. Плюс url-safe алфавит и отсутствующая добивка `=`. Разбираются все
  варианты (`_decodeB64Loose`), IPv6 отдаётся без скобок — sing-box их не ждёт.
- Конфиг sing-box берётся как есть: его outbound-ы уже в целевом формате,
  служебные (`direct`, `block`, `selector`, `urltest`) отсеиваются по типу.

**Проверено (2026-08-24), обе половины:**
`test/sub_formats_test.dart` — 15 тестов на НАСТОЯЩИХ функциях из main.dart
(не на копиях: копия расходится с оригиналом на первой же правке). Плюс живой
прогон: из реальных серверов подписки собран Clash-YAML, разобран новым
парсером, отдан `sing-box.exe check` (принят) и запущен — vless+Vision 448 мс,
trojan 631 мс, hysteria2 683 мс, у всех верный exit-IP, 3 МБ за 1.16 с,
ошибок в логе ядра ноль.

**Грабля методики, снова та же:** первый прогон дал EOF на двух серверах, и это
выглядело как ошибка разбора. Контроль (те же серверы из ссылок, старым

минуту: и контроль, и Clash прошли полностью. Без контроля правился бы

## Известные баги, уже исправленные (не переоткрывать)

- `Uri.userInfo` не декодирует percent-encoding — UUID/пароли с `%3D` и т.п. нужно
  прогонять через `Uri.decodeComponent`.
- VMess `security=auto` + TLS → sing-box сам тихо переключается на `zero` (без
  шифрования VMess-заголовка) — часть серверов такие соединения молча рвёт. Форсим
  `aes-128-gcm` вместо `auto`, когда TLS включён.
- Пути к `sing-box.exe`/`xray.exe`/конфигам — всегда через
  `File(Platform.resolvedExecutable).parent.path`, никогда не относительные
  (текущий рабочий каталог процесса не гарантированно совпадает с папкой .exe).
- `sing-box.exe`/`xray.exe` бандлятся в билд через `install(FILES ...)` в
  `windows/CMakeLists.txt` (та же директория, куда кладётся `flutter_windows.dll`).
- Старый формат DNS-серверов sing-box (`{"address":...}`) удалён в новых версиях —
  нужен новый: `{"type":"udp","tag":...,"server":...,"detour":...}`.

## Сборка Android — три препятствия подряд, все внешние

APK собирается, но ни одна из нужных переменных окружения на машине не
задана, и каждая даёт свою ошибку. Рабочая команда целиком:


1. **`No Android SDK found`** — SDK лежит в `C:\dev\android-sdk`, но
   `ANDROID_HOME` не задан.
2. **`JAVA_HOME is not set`** — отдельного JDK и Android Studio на машине НЕТ
   вовсе (проверено по реестру и списку установленных программ). JDK приехал
   вместе с SDK: `C:\Program Files\Android\openjdk\jdk-21.0.8`.
3. **`java.io.IOException: Unable to establish loopback connection`** — не про
   сеть. Петля у Java исправна (проверено отдельной программой: и `127.0.0.1`,
   и `::1` работают), спотыкается Gradle о **кириллицу во временной папке**:
   `C:\Users\Абилова Зарина\AppData\Local\Temp`. Отсюда и `C:\dev\gradle-tmp`,
   созданный при прошлой удачной сборке 13 августа. Задавать надо И
   `java.io.tmpdir`, И `TMP`/`TEMP`.

**Грабля, из-за которой это легко проглядеть: `flutter build apk` выходит с
